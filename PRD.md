# Product Requirements Document (PRD) — The Lenny Growth Assistant

**Version:** 1.0 (Production Release)  
**Status:** Approved & Released  
**Target Audience:** Product Managers, Founders, Growth Engineers, Evaluators  

---

## 1. Executive Summary & Problem Framing

### 1.1 The Problem
Lenny Rachitsky's podcast ("Lenny's Podcast") is one of the premier repositories of practical product management, company building, and growth strategy in the technology industry. Across more than 300 deep-dive interviews and thousands of hours of audio, guests share hard-won frameworks, metrics, organizational tactics, and operational philosophies.

However:
- **Search Friction:** Traditional keyword search across 300+ transcripts cannot answer complex cross-episode thematic queries (e.g., comparing Airbnb's founder-led design philosophy with Figma or Linear's operational cadences).
- **Hallucination Risk:** Generic commercial LLMs frequently hallucinate anecdotes, misattribute quotes, or confuse advice from different leaders.
- **Actionability Gap:** Summaries generated by generic tools lack actionable narrative structure, publication polish, and verifiable traceability back to original audio timestamps.

### 1.2 The Solution: The Lenny Growth Assistant
The Lenny Growth Assistant is a full-stack, enterprise-grade AI knowledge and writing application. It provides:
1. **Grounded Conversational Intelligence:** Dual-orchestrator conversational search (Direct Vector RAG and Autonomous Pi Coding Agent) backed by PostgreSQL `pgvector`, verifying every citation against exact transcript chunks, guests, and video timestamps.
2. **Ship 30 for 30 Writing Studio:** A durable, background-queued long-form writing engine that transforms podcast research into compelling, structured ~650–1,250 word essays following Nicolas Cole and Dickie Bush's publication frameworks.
3. **Interactive Artifact Workspace:** A split-screen writing environment featuring markdown editing, real-time sandboxed HTML rendering, automated immutable version history, and non-blocking asynchronous AI revisions.
4. **Dynamic Provider Agility:** Runtime switching between local offline models (Ollama `qwen2.5:1.5b` with `nomic-embed-text:v1.5`) and high-throughput cloud inference (NVIDIA NIM `openai/gpt-oss-20b`).

## 3. Success Metrics & Validation Benchmarks

- **Corpus Integrity:** 303 episodes, 17,365 chunks indexed in PostgreSQL `pgvector` with 768-dimensional embeddings (`nomic-embed-text:v1.5`).
- **Citation Precision:** 100% of displayed citations must trace to real transcript chunk IDs, guest names, titles, and video timestamps.
- **Hallucination Mitigation:** If transcripts lack sufficient evidence, the assistant must explicitly abstain rather than fabricate advice.
- **Worker Reliability:** 100% of background writing and revision jobs must survive worker restarts, maintain heartbeats in PostgreSQL, and avoid corrupting brief snapshots.
- **Quality Gate Honesty:** Drafts that deviate from target word counts or missing citations must be persisted and accessible to users with transparent diagnostic feedback rather than failing invisibly.
- **Security Isolation:** Rendered HTML must be isolated inside restrictive sandboxed iframes without script execution permissions (`sandbox=""`).

## 4. Scope & Feature Specifications

### 4.1 In Scope
- **Conversational RAG (Direct):** Fast semantic retrieval using cosine distance ranking, diversified duplicate suppression, and conversation history buffer.
- **Autonomous Pi Coding Agent:** Multi-turn ReAct agent running in Node.js, invoking authenticated internal backend tools (`search_transcripts`, `get_transcript_context`) via HTTP.
- **Durable Essay Generation:** Redis-queued background jobs (with PostgreSQL fallback polling) executing structured 4-step research and writing pipelines with bounded revisions.
- **Artifact Management:** PostgreSQL-persisted writing artifacts with monotonic version numbering (`WritingArtifactVersion`), diff retention, and manual save actions.
- **Asynchronous AI Revision:** Non-blocking revision jobs processed by background workers, updating artifacts without frontend timeouts.
- **Sanitized HTML Preview:** Server-side sanitization stripping `<script>`, `<iframe>`, and `javascript:` URIs, rendered in isolated iframes.
- **Multi-Model Runtime Switching:** Real-time authoritative switching between Ollama and NVIDIA NIM cloud endpoints with provider-aware snapshots.

### 4.2 Out of Scope (Current Release)
- Multi-tenant user login and enterprise RBAC (single-tenant local workstation deployment).
- Fine-tuning base LLM weights on podcast transcripts (RAG architecture preferred for traceability).
- Live podcast audio transcription ingestion pipeline (pre-ingested curated corpus).

## 5. User Workflows & Acceptance Criteria

### Workflow 1: Grounded Conversational Q&A
1. User enters query: *"What is Brian Chesky's perspective on founders being involved in details?"*
2. System retrieves relevant transcript chunks via vector similarity.
3. Assistant synthesizes response citing `[Source 1: Brian Chesky - Brian Chesky's new playbook]`.
4. User clicks citation chip: drawer opens showing exact excerpt, episode guest, and YouTube timestamp link.
5. User asks follow-up: *"How does he contrast this with standard division of labor?"* System maintains session context.

### Workflow 2: Session-Grounded Essay Generation
1. In chat, user clicks "Create Essay from this Answer".
2. System populates the Essay Composer with topic, key takeaways, and source session ID.
3. User selects 650-word target and "Analytical" tone, then clicks "Generate Essay".
4. Background worker receives queued job, extracts session chunks, drafts essay adhering to Ship 30 for 30 methodology.
5. System displays real progress stages (`Researching`, `Drafting`, `Evaluating`).
6. Finished essay opens automatically in the Artifact Viewer.

### Workflow 3: Artifact Editing, Versioning, and HTML Preview
1. User inspects generated markdown in the Workspace editor.
2. User toggles to "HTML Preview": system renders clean, typography-formatted HTML inside sandboxed iframe.
3. User edits text and clicks "Save Version": system persists Version 2 with updated word count and timestamp.
4. User opens Version History drawer to review past versions or restore prior revisions.

### Workflow 4: Asynchronous AI Revision
1. In the Artifact Viewer, user enters revision prompt: *"Add a concrete bulleted checklist for product managers at the end."*
2. System returns immediate job ID (HTTP 202); UI shows active revision progress.
3. Background worker executes targeted revision preserving citations.
4. On completion, UI updates artifact to Version 3 with the revised checklist.

## 6. Risks, Trade-offs & Mitigations

| Risk | Impact | Mitigation Strategy |
| :--- | :--- | :--- |
| **Local Model Slowness** | Local CPU inference on `qwen2.5:1.5b` can take 60–120s for long essays. | Durable background jobs with Redis queue, stage-by-stage polling, non-blocking UI. |
| **Strict Schema Incompatibilities** | Worker metadata injection causing validation failure (`BUG-002`). | Separated `brief` payload from `snapshot` provider metadata with `unpack_job_brief()`. |
| **Out-of-Range Draft Length** | Deterministic quality gates rejecting drafts. | Bounded length correction attempt; if still out of range, persist draft and display transparent diagnostics banner. |
| **XSS via User/AI Content** | Malicious script execution in artifact preview. | Dual-layer security: Server-side HTML tag sanitization + sandboxed client iframe without `allow-scripts`. |
| **Provider Downtime** | Cloud NVIDIA API key exhaustion or rate limit. | Configurable explicit fallback to local Ollama with clear UI provider indicators. |
